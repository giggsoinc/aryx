Aryx Dashboard Guide — C01→C15

End-to-end reference for the business intelligence dashboard pipeline: a natural-language objective goes in, a governed, chart-rendered dashboard comes out — with two hard validation gates (C09, C13) in between so nothing the model invents ever reaches the screen. This page also walks through how the planner prompt actually works (andie_planner/prompt.py) — its discipline rules, its four builder variants, and its repair loops.

Stages: C01–C15 Prompt version: 1.11 Two hard gates: C09 (spec) · C13 (results) Source of truth: src/aryx + apps/web

1. What the dashboard pipeline is

Turns a plain-English objective ("show me renewal health by region") into a working BI dashboard — without ever letting an LLM compute a number, invent a column, or silently drop a chart. The LLM only drafts a candidate spec (which columns, operations, chart types to use); every computation runs in deterministic, testable Python, and every LLM output passes a grounding check plus a formal validation gate before it can affect anything downstream.

One real LLM call

Of the 15 stages, only C08 (drafting) calls a frontier model for its core output. C14 has one optional LLM call (chart/section titles only, never values).

Two hard gates

C09 grades the spec before anything executes. C13 independently recomputes and grades the results after execution. Neither re-litigates the other's decisions.

Never-raise contract

Every stage returns a typed status (valid / invalid / controlled_error / controlled_failure, approved / approved_with_warnings / rejected, etc.) instead of throwing — failures are visible, not silent.

Design tenet, repeated across C08–C14 docstrings: C08 "strips and keeps going, warns" on anything ungrounded; C09 "rejects and reports" on the same class of problem, as a hard gate. C11–C14 explicitly say they are "never a re-litigation of C09's decisions" — each stage trusts the upstream gate and only re-checks its own structural concerns.

3. Cross-cutting principles

Never invent

Every column, operation, chart type, and cross-reference the LLM proposes is checked against real approved resources (C08's ground.py) or real profiled data (C09/C13). Anything unsupported is stripped and recorded as a warning — never silently kept, never approximated.

Two different failure philosophies, on purpose

C08 grounds by stripping and warning (degrade gracefully). C09 and C13 are hard pass/fail gates — the same class of problem that's a warning in C08 is a blocking error one/five stages later.

Typed outcomes, never exceptions

PlannerResult, ValidationReport, ExecutionRun, PostExecutionReport, DashboardModel all carry an explicit status enum. A stage's own internal crash becomes a typed rejection (e.g. C13's recomputation_failed), not an unhandled exception.

Additive stages can never downgrade a result

C10 (preprocess) and C11 (compile) chaining inside andie_planner/run.py are wrapped in broad except Exception (annotated noqa: BLE001) specifically so a best-effort follow-on stage can never block or corrupt the primary C08/C09 outcome.

4. C01–C07 — grounding the planner (brief context)

Everything before C08 builds the planning context the prompt is allowed to see:

  • C01 — objective, audience, preferences
  • C02–C04 — ingest a dataset; profile + semantically tag its columns, including real observed sample_values for categorical ones
  • C05/C06 — land and profile the knowledge graph (verified, single-hop graph_paths only)
  • C07 — assembles it all (approved columns, graph paths, operations, chart types) into the one payload C08's prompt is built from

Dashboard-specific logic starts at C08, so C01–C07 aren't detailed further here — see planning/* (assemble.py, catalogues.py, models.py).

5. C08 — Aryx Insight Orchestrator

Package: src/aryx/andie_planner/. This is the only stage that calls a frontier LLM to produce the dashboard's actual content (which KPIs, which analyses, which charts). Its output is explicitly a candidate, non-executable spec — nothing here computes a value.

5.1 Prompt anatomy — how prompt.py actually works

prompt.py builds a (system, user) message pair — it never calls the LLM itself; generate.py does that via complete_json. All four builder functions in the file share one system prompt (_SYSTEM, versioned PROMPT_VERSION = "1.11") and differ only in what goes in the user message.

The system prompt's discipline (six rules, always present)

#RuleWhat it means
1Closed vocabulary onlyReference only column names, operations, chart types listed in "approved resources" — nothing invented, however useful it seems.
2Include ⇒ verifyEvery column/operation/chart type a KPI/analysis/visualization uses must appear in approved resources, or the whole item is dropped with a warning — never approximated.
3Filters need a real valueA filter with only a column name is rejected outright, even if the KPI's name implies one (e.g. "Active X Count" with no status filter). If the column has sample_values, copy one verbatim; if not, drop the KPI/analysis and warn — never guess.
4Say so, don't guessAnything the objective needs but approved resources don't support goes in warnings, not a padded approximation.
5Layered draftingCore KPIs first, then one layer deeper — breakdowns, trends, edge cases (small samples, missing values) — with reasoning captured in assumptions.
6JSON onlyNo preamble, no markdown fences, no explanation outside the JSON object.

Rules 3 and 5 are adapted, not invented fresh: the no-invention/state-uncertainty posture borrows from andie-jr's bug-triage discipline (only that posture transfers, not its verdict shape); the layered-drafting framing borrows from Andie's Deep mode (core → mental model → what breaks → next level down) — again, only the shape transfers, not Deep mode's teaching tone.

A large block maps data shape to chart type, explicitly instructing the model never to default to bar/table when a more specific type fits better:

5.2 Four prompt builders — one discipline, four shapes

FunctionWhen usedWhat's different in the user message
build_planner_prompt() Fresh draft, single dataset One flat approved_columns list + graph paths/operations/charts. Requests 10–12 visualizations, 3–5 business_questions, plus full kpis/analyses/visualizations/assumptions/warnings.
build_workspace_planner_prompt() Fresh draft, multi-dataset workspace Resources grouped per dataset_id (never flattened — same column name can mean different things per dataset). Every KPI/analysis declares its own dataset_id; cross-dataset column mixing is an explicit rejection reason.
build_delta_prompt() Ask-to-visualize — one new chart on an already-approved dashboard Reuses _SYSTEM unchanged. Frames the model as extending: given existing_kpis/existing_analyses, prefer reusing one via source_ref; draft new only if genuinely needed. Caps output at 1 new KPI, 1 new analysis, exactly 1 new visualization.
build_filter_repair_prompt() Narrow micro-repair for a known missing_filter_value defect Own smaller system prompt (not _SYSTEM) — fixes named, already-identified defects only. One item per broken filter with real sample_values; reply is an exact verbatim value or null, never a new draft.
Recurring guard inside every builder: right before the "return JSON" instructions, each prompt re-states the filter/sample_values rule one more time as a final self-check — the file's own comment calls a missing filter value "the most common reason a draft gets rejected," so the prompt asks the model to re-verify it once more immediately before replying.

5.3 Repair loops — two different kinds, never confused

prompt.py exposes two distinct repair helpers, for two different failure points:

HelperTriggered whenBehavior
repair_prompt(user, reason) Raw LLM response is malformed or empty (missing business_questions/kpis, or a broker exception) Re-states: reply with ONLY the JSON object, exact keys. One retry only (generate.py's _MAX_ATTEMPTS = 2).
append_repair_constraints(user, constraints_text) Spec was well-formed but C09 rejected it for itemized reasons (repair_constraints_text names the exact defect per error) Framed as one Kaizen cycle (Andie's fix → verify → iterate): change only what each error names, keep every unflagged item exactly as-is. This is run.py's single bounded repair retry against C09 — a separate cap from C08's malformed-response retry above.
Both caps are enforced independently: C08's loop caps at _MAX_ATTEMPTS = 2 for malformed JSON; C09's repair cap (MAX_VALIDATION_ATTEMPTS = 2) is enforced server-side by run_spec_validation(), counting prior attempts via SpecValidationStore — a caller retrying the endpoint directly cannot bypass it.

6. C09 — Pre-execution specification validation

Package: src/aryx/spec_validation/. The first hard gate: where C08 warns and keeps going, C09 treats the same class of evidence as disqualifying.

6.1 Ten named checks (checks.py → ALL_CHECKS)

#CheckWhat it enforces
1check_json_schemaAt least one business question + one KPI
2check_column_existencePromotes C08's unapproved_column/unknown_dataset warnings to hard errors
3check_graph_path_groundingAssumption text referencing path_* tokens must match an approved graph path
4check_type_compatibilityNumeric ops (sum/average/median) require a real numeric measure — closes a gap where a KPI with no measure used to compile against an empty column and fabricate value=0.0
5check_operation_whitelistPromotes unsupported_operation
6check_formula_validityRatio/percentage KPIs need both operands; missing_filter_value stays a hard error on purpose — an operand with filter=None silently becomes "count of everything," judged worse than a regeneration
7check_division_by_zero_policyZero-denominator policy must be exactly return_null_with_warning — the only value C12/C13 implement
8check_chart_axis_compatibilityStructural shape rule per chart family (crosstab/gantt/survival/scatter/bubble/histogram/radar/graph_relation); dangling refs downgrade to warnings (C08 self-heals them already)
9check_lineage_declarationEvery KPI/analysis must declare its source columns/operations (or a graph_path_id for graph_relation)
10check_claim_safetyBlocklists causal/predictive language ("forecast", "will cause", "due to"…) in questions/assumptions

6.2 Orchestration

  • models.py — ValidationReport, RepairRequest / RepairErrorConstraint, ControlledFailure, MAX_VALIDATION_ATTEMPTS = 2.
  • validate.py — validate_spec() runs all 10 checks into one report; _build_repair_request() builds structured, per-error correction constraints (allowed replacement columns/operations/chart types); repair_constraints_text() renders these as plain text for the retry prompt, using difflib.get_close_matches to suggest the likely intended column.
  • run.py — run_spec_validation() enforces the attempt cap server-side before running checks.

7. C10 — Preprocessing & transformation

Package: src/aryx/preprocess/. Chained automatically onto an approved C09 spec (andie_planner/run.py::_run_c10_for_approved), one call per referenced dataset.

  • policy.py — derives a deterministic conversion/null policy per column from C03's profile.
  • transform.py — applies the policy with a soft per-column safety gate: if a column's conversion failure rate exceeds a threshold, that column reverts to its original raw values rather than silently corrupting data ("C10 reverts columns, never drops rows").
  • Produces an immutable transformation log — never mutates the raw C02 snapshot. C12's data.py replays this exact log at execution time so both stages see identical converted values.

8. C11 — Execution compiler

Package: src/aryx/execution_compiler/. Turns an approved DashboardSpec into a typed, acyclic execution DAG built exclusively from vetted templates — never arbitrary generated code.

  • templates.py — TEMPLATES: dict[str, frozenset[str]], the exhaustive allowlist of template name → required parameter keys (filter_equals, safe_ratio, grouped_safe_ratio, row_points, survival_curve, graph_relation_count, …). A node using any other template, or mismatched parameters, is rejected.
  • compile.py — compile_plan_for_spec(spec, dataset_row_count=None) -> ExecutionPlan. _compile_kpi() builds filter → measure/count → (for ratios) safe_ratio chains; _compile_analysis() dispatches on Analysis.operation to the matching template. After binding, runs 5 structural checks; any hard-failure code sets compilation_status = "rejected".
  • models.py — ExecutionNode (template + parameters + depends_on), CompilationIssue, ExecutionPlan (carries kpi_final_node/kpi_lineage_nodes/analysis_node maps so C12/C13 don't guess from node-id naming).
  • validate.py — validate_bindings() (unknown template / wrong params / dangling dep / duplicate id), is_acyclic() (Kahn's algorithm), check_ratio_operand_operations(), check_resource_limits() (node-count cap, DEFAULT_NODE_LIMIT = 200).

Data flow: input = approved DashboardSpec; output = ExecutionPlan, persisted via ExecutionPlanStore, exposed only as a read-only API (no run endpoint — it's compiled automatically right after C09 approval).

9. C12 — Deterministic analysis execution

Package: src/aryx/analysis_execution/. Runs a compiled C11 plan against real, C10-converted rows — the first stage to produce real business values. Triggered on-demand (POST /execution-run/run), never auto-chained.

  • data.py — load_typed_rows() re-parses the raw C02 snapshot and re-applies the exact conversion policy C10 already logged, so C12 executes against the same values C10 described.
  • execute.py — run_plan() executes nodes in topological order; each dispatches to one of ~24 template handlers. A failing node is caught and recorded in errors, skipped — dependents simply get no result rather than crashing the whole run. resolve_graph_relation_nodes() resolves a graph_relation_count node's path_id to a concrete source/relationship/target triple from GraphProfileStore right before execution.
  • models.py — KpiResult, AnalysisResult/AnalysisResultRow (wide shape covering grouped scalar, crosstab cell, scatter point, gantt span, survival point, histogram buckets), ExecutionRun (completed | failed | partial).
  • run.py — run_analysis_execution(): loads the latest compiled plan (returns immediately if compilation_status == "rejected"), executes, computes _display_value() (a None value renders as an em dash "—", never fabricated as "0%"), then calls C13 and attaches the report — wrapped so a C13 failure never loses the C12 result.
graph/reader.py is C12's only graph touchpoint: when a compiled plan contains a graph_relation_count node, execute.py obtains a GraphReader via dependency injection and calls count_by_relationship(source_type, relationship, target_type, direction) — the only reader method the dashboard pipeline exercises. Every other operation reads exclusively from the relational dataset snapshot (C02/C10); no other pipeline stage touches the graph.

10. C13 — Post-execution validation

Package: src/aryx/post_execution_validation/. The second hard gate — mirrors C09 one stage later: C09 grades the spec before execution, C13 grades the results after. This is the stage the "close silent-failure gaps" commits target directly.

10.1 Independent recompute

recompute.py re-executes the compiled plan from scratch (same load_typed_rows + run_plan primitives C12 uses) — the stored run's values are cross-checked against a fresh computation, never trusted at face value.

10.2 Seven named checks (checks.py, A–G)

IdCheckWhat it catches
Acheck_result_identityEvery reported ID must be one the spec declared — invented ID is a hard error, expected-but-missing is a warning
Bcheck_aggregation_correctnessRecomputes every KPI value AND analysis row, compares at 1e-6 tolerance — a structurally valid but numerically wrong result is still blocked
Ccheck_sample_size_reconciliationNumerator can never exceed denominator; no negative counts
Dcheck_evidence_lineagelineage.operation_ids must exactly equal the nodes C11 actually compiled; dataset_version must match
Echeck_no_invented_columns / _kpisEvery lineage column must be real per the profile; every reported id must trace to a compiled node
Fcheck_result_shapeTypes must match schema (a numeric field that became a string fails even if still valid JSON)
Gsmall_sample_warningsSample below SMALL_SAMPLE_THRESHOLD = 30 is flagged, never rejected
The specific silent-failure fix in this stage: null_result_warnings — C12's safe_ratio/grouped_safe_ratio only ever implemented the "return null" half of the return_null_with_warning policy; nothing actually emitted the promised warning. C13 now surfaces every None-valued KPI/row as a null_result warning so a blank chart is never mistaken for "the feature is broken."

validate_execution() aggregates all 7 checks into a PostExecutionReport: rejected if any errors, else approved_with_warnings if warnings exist, else approved. eligible_for_dashboard = not errors is the exact flag C14 gates on. Never raises — even a recompute exception becomes a recomputation_failed error that forces rejected / eligible_for_dashboard=False.

11. C14 — Dashboard composition

Package: src/aryx/dashboard_composition/. Arranges an approved spec's already-validated results into an ordered, readable dashboard model — never computes anything, never alters a governed value/formula/axis/ID.

11.1 compose.py — five mechanical steps

  1. Build components — one per approved visualization, bound only if the run actually produced a value for that source_ref (a kpi_card bound to a non-KPI id is flagged chart_type_mismatch, never fabricated).
  2. Apply layout constraints — KPI cards are never capped; other charts capped at maximum_primary_charts (default 12); excess is reported as layout_limit_exceeded, never silently dropped.
  3. Prioritize — cards first, then charts; positions renumbered.
  4. Group into sections — cards share one section_summary; remaining charts group by their analysis's group_by column; uncategorized ones fall into section_charts.
  5. Attach warnings — pulls C13's run.validation.warnings forward onto the owning component, at per-group granularity (e.g. a small_sample_size warning attaches only to the one affected region's component).

A final revalidate() structural self-check (duplicate component IDs, empty section titles) runs again after any LLM narration. Composition also surfaces a no_visualizations issue when the approved spec declared none — the "C14 masking empty output" fix: downstream code now distinguishes "nothing composed yet" from "the spec legitimately has nothing to show."

11.2 The one optional LLM step — narrate.py

suggest_titles() asks for a dashboard title plus one title per section_id — never components, IDs, or values. Any mismatch between returned and expected section IDs discards the whole suggestion (never a partial apply); any exception falls back silently to deterministic titles. compose_dashboard() re-runs revalidate() after narration and discards corrupted titles ("C14 discarding LLM titles — failed revalidation").

Hard gate on C13: run.py::compose_dashboard() checks run.validation.eligible_for_dashboard first — if falsy, returns an invalid DashboardModel with issue results_not_eligible immediately. Composition never runs against unvalidated results.

12. C15 — Frontend dashboard renderer

The actual final interface — no LLM, no server-side compute. Merges the persisted DashboardModel (C14) with the already-computed ExecutionRun (C12/C13) into UI-ready values. Never recomputes a governed KPI formula client-side.

  • src/aryx/dashboard_render/models.py — the only backend-touching piece: RenderTelemetry / AccessibilityChecks, an audit trail (never a gate).
  • apps/web/components/planner/DashboardSpecPanel.tsx — renders C08's PlannerResult, handling all four statuses distinctly (controlled_error in red with the error code; controlled_failure in rose showing C09's exhausted rejection codes; otherwise the spec itself plus a non-blocking client-side RichnessIndicator heuristic — thin if <3 KPIs, <4 visualizations, or zero substantive assumptions — that only flags, never rejects).
  • apps/web/components/planner/DashboardRenderer.tsx — the actual C15 renderer. Polls every 4s (this panel has no run trigger of its own; its data comes from sibling panels).

12.1 Chart-type dispatch

Chart-type vocabulary is fully delegated to Plotly via lib/plotlySpecs.ts's 21 build*Spec builders (bar, line, area, step, donut, box_plot, heatmap_matrix, calendar_heatmap, sankey, treemap, sunburst, waterfall, pareto, histogram, scatter, bubble, gantt, survival, grouped_bar, slopegraph, radar — a few, like buildCalendarHeatmapSpec, are thin aliases onto another builder), all rendered through one shared <PlotlyChart spec={...} /> component.

BarChart.tsx no longer exists as a dedicated component — bar charts (and every other family) now go through the unified ROWS_SPEC_BUILDERS dispatch table keyed by component.type, calling into plotlySpecs.ts. Only non-chart types (kpi_card, table) are still bespoke-rendered inline.
BucketTypes
BAR_LIKE_TYPESbar, line, area, step, donut — support SingleValueFallback

A user sees "the approved spec declared no visualizations," never a blank panel indistinguishable from a loading state.

14. Failure & HITL model

StageFailure surfaces asWhat happens next
C08PlannerResult.status = controlled_errorLLM/broker exception or malformed JSON after 1 retry — terminal, nothing to approve
C09PlannerResult.status = controlled_failureSpec rejected after 1 bounded repair retry — terminal; UI shows the exact rejected error codes
C11ExecutionPlan.compilation_status = rejectedC12 checks this first and refuses to execute a rejected plan
C12ExecutionRun.status = failed | partialIndividual failing nodes are skipped, not fatal to the whole run; still passed to C13
C13PostExecutionReport.status = rejected, eligible_for_dashboard = FalseC14 refuses to compose — dead end until re-run
C14DashboardModel.composition_status = invalidFrontend shows the composition issue instead of a broken dashboard

HITL is explicit and human-facing at exactly two points: approving/rejecting a C08 spec on DashboardSpecPanel, and triggering a C12 run on ExecutionRunPanel. Every other stage chains automatically once its predecessor is approved.

15. How to extend the pipeline

  1. New chart type? Add it to the prompt's chart-type guide (prompt.py's _SYSTEM) and supported_charts catalogue → add its structural rule to C09's check_chart_axis_compatibility → add a build*Spec function in plotlySpecs.ts and register it in the right type bucket in DashboardRenderer.tsx.
  2. New analysis operation? Add to supported_operations catalogue and the chart-type guide → add a template + param set to C11's templates.py and a compile branch in _compile_analysis() → add an execution handler in C12's _exec_node() → add a check in C13's _ANALYSIS_ROW_CHECKS if it produces its own row shape.
  3. New C09 validation rule? Add a pure function to ALL_CHECKS in checks.py; keep it deterministic and returning (CheckResult, errors, warnings) — never network/LLM calls inside a check.
  4. Never let the LLM compute a value, invent a column/chart type, or bypass the C09/C13 gates — every extension point above keeps the LLM confined to drafting vocabulary that deterministic code then verifies and executes.
